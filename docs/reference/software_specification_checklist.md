# ソフトウェア仕様書：必要項目チェックリスト

> **目的**：ソフトウェアの種類・規模・開発手法を問わず、仕様書の作成・レビュー時に必要項目を確認するための汎用チェックリスト。  
> **使い方**：各項目を `[x]`（記載済み）、`[ ]`（未記載・要確認）、`[N/A]`（該当なし）で評価する。該当しない項目は、必要に応じて理由を記録する。  
> **重要**：すべての項目を機械的に必須とするものではない。対象ソフトウェアのリスク、規模、利用者、規制・契約上の要求に応じて適用範囲を決める。

- [ ] 文書の状態（草案、レビュー中、承認済み等）が分かる
- [ ] 変更履歴と変更理由が記録されている
- [ ] 関連文書、参考資料、外部規格への参照がある
- [ ] 用語、略語、記号、命名規則が定義されている
- [ ] 未決事項、仮定、判断待ちの事項が区別されている

## 16. 要件一覧表（推奨フォーマット）

重要な要件は、本文とは別に一覧表で管理すると追跡しやすい。

| ID | 要件名 | 要件・期待動作 | 優先度 | 根拠・出典 | 検証方法 | 状態 |
|---|---|---|---|---|---|---|
| REQ-001 | 例：入力検証 | 入力値が許容範囲外の場合、処理を開始せずエラーを返す | 高 | 利用者要望 | 異常系テスト | 未着手 |

**推奨事項**
- IDは一意で、変更後も追跡できるようにする。
- 優先度は例として「必須／重要／任意」など、プロジェクト内で定義した区分を用いる。
- 状態は例として「未着手／検討中／確定／実装済み／検証済み」とする。
- 要件の粒度は、原則として一つの検証可能な要求に一つのIDを割り当てる。

## 17. Claude Opus 5.5で仕様書を作成する際の確認事項

このチェックリストを使って仕様書を生成する場合は、次の点も確認する。

- [ ] 依頼内容にない要件、数値、機能、外部サービス、技術選定を事実として捏造していない
- [ ] 不明点を「要確認」「仮定」「提案」に分け、確定事項と混同していない
- [ ] 入力資料・既存コード・関連文書が提供されている場合、それらを確認したうえで記述している
- [ ] 仕様の根拠となる情報と、AIによる提案・推測が区別されている
- [ ] 不足情報があっても、作成可能な範囲の草案と未決事項一覧を提示している
- [ ] 仕様の内部矛盾、実現可能性、テスト可能性を自己レビューしている
- [ ] 実装済みと断定する場合、コードや実行結果などの根拠がある
- [ ] 外部情報や技術仕様の確認が必要な場合、信頼できる一次資料を優先している
- [ ] 最終出力がMarkdownとして読みやすく、見出し・表・コード表記が適切である

## 18. 最終判定

- [ ] **目的・スコープ**：何を作るか、何を作らないかが明確
- [ ] **機能**：主要機能、入力、出力、異常時の動作が明確
- [ ] **環境**：必要環境、依存関係、導入・実行方法が明確
- [ ] **品質**：必要な性能・安全性・信頼性等が具体化されている
- [ ] **検証**：要件を満たしたか判定する方法が定義されている
- [ ] **未決事項**：未確定事項、仮定、リスク、対象外事項が明示されている
- [ ] **追跡可能性**：要件とテスト・実装の対応を確認できる
- [ ] **承認**：必要なレビューと承認が完了している

### 判定の目安

- **作成開始可能**：目的・スコープ・主要ユースケースが把握でき、未決事項が明示されている
- **実装開始可能**：主要機能、入出力、異常時の挙動、環境、受入れ条件が十分に定義されている
- **リリース判定可能**：重要要件の検証結果、既知の制限、運用・復旧手順、承認状況が確認できる
